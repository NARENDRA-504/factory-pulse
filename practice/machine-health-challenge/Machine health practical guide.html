Machine health data science practical guide

Start here

This manual takes you from opening the dataset to exploratory data analysis, cleaning, feature engineering, chronological splitting, model training, evaluation and a local prediction service. Each step states what to do, why it matters and what to save. You perform the experiment; this package does not train a model or alter either live app.

Your business question

Using readings available now, which machines are likely to experience a failure in the next two hours? Prioritize the next 30 minutes as Critical, and the following 30 to 120 minutes as Suspect. Normal means no failure in the next two hours with sufficient follow-up. This target predicts future failure proximity; it does not diagnose a current fault.

What is inside

The raw file has 81,375 packets representing 80,640 unique observations from 40 fictional machines over 14 days. There are 120 simulated failures. Sampling is every 10 minutes per machine. Temperature, vibration, RPM, current, motor load, pressure, coolant flow, ambient temperature and service age provide candidate inputs.

Important limit

All values, machines and failure labels are synthetic. Some failures have no early precursor. Learning a generated pattern is not evidence that a model will prevent failures on real equipment. The packet quality flag is not a machine-health diagnosis. Machine specifications are illustrative, not approved safety thresholds.

Understand the tables and prediction labels

Where each file belongs

telemetry_raw.csv contains dirty sensor packets. machine_registry.csv lists canonical machines, families and plants. machine_id_crosswalk.csv resolves aliases. training_labels.csv holds the target for each packet. failure_events.csv supplies outcome times for evaluation. maintenance_log.csv describes repair actions and when those records became available.

How to join

Clean and deduplicate packets before joining labels on packet_id. Validate the join as one-to-one. Canonicalize machine IDs using the crosswalk and compare the cleaned identity to the identity in the label file. Never join by row number: the raw CSV is intentionally shuffled.

Labels you may train on

Normal: next failure is outside 120 minutes. Suspect: next failure is more than 30 and at most 120 minutes away. Critical: next failure is more than zero and at most 30 minutes away. At the failure time itself, a machine already down is Ineligible. Unknown marks insufficient follow-up near the dataset end. Exclude Unknown and Ineligible from this specific predictive task.

Why the classes are uneven

Before cleaning there are 77,858 Normal, 1,080 Suspect and 360 Critical observations, plus 902 Ineligible and 440 Unknown. A model predicting Normal for every eligible row would appear about 98.2 percent accurate and detect no failure warnings. You must measure each class separately.

Forbidden model inputs

Keep next_failure_at_utc, next_failure_mode, health_priority and future repair outcomes outside X. These reveal the answer. failure_events.csv is evaluation evidence, not a source of future features. Maintenance data may be joined only when available_at_utc is at or before the observation. The provided starter does not use maintenance records as features.

Write a short target_definition.md explaining the prediction time, 120-minute horizon, class meanings, exclusions and intended users. This avoids changing the problem halfway through training.

Perform the first EDA before cleaning

Meaning and purpose

EDA means exploratory data analysis. First understand how the data was recorded and where it is unreliable. Do not immediately fill all missing values or delete every unusual reading: a genuine warning may itself be unusual.

Check structure

Load raw data initially as text so decimal commas, missing cells and sentinels remain visible. Inspect shape, column names, ten sample rows, unique values in units and quality flags, and missing counts per column. Count unique packet IDs and repeated IDs separately. Compare machine IDs to the registry and crosswalk.

Check time

Parse both supported timestamp formats as UTC. Count failures to parse, sort by canonical machine and time, and plot observations per machine per day. Expected canonical cadence is 10 minutes. Count gaps, repeated timestamps and changes in sensor availability. Missing rows and missing sensor cells are different problems.

Check numeric distributions

For each sensor inspect count, median, minimum, maximum, interquartile range and percentiles. Start plots separately by unit; combine only after conversion. Draw histograms and box plots by machine family. Look for -9999, implausible values, zero runs and constant blocks. Write hypotheses rather than declaring every extreme a failure.

Inspect outcome balance

Use labels for descriptive analysis in the training period. Plot Normal, Suspect and Critical counts and failure counts by family and plant. Investigate class imbalance and repeated observations around one event. Do not explore final test outcomes repeatedly to choose features.

Save

Save raw_audit.json, missingness.csv and notes with five findings, their likely effects and proposed checks. The starter creates initial reports, but your interpretation is the main learning task. Report exact row counts at each subsequent stage.

Make useful EDA charts

Coverage chart

Plot date on the horizontal axis and observation count on the vertical axis, grouped by machine or plant. It answers whether all machines were observed consistently. Make this before and after deduplication to reveal inflated packet counts.

Sensor histograms and box plots

Use normalized numeric values. A histogram shows shape and outliers; family-specific box plots reveal different operating ranges. A grinding machine and a milling machine need not share the same baseline. Do not treat an asset’s rated RPM as a universal alarm threshold.

Time series

Choose one canonical machine and plot each sensor against UTC time. Add known failure times to the training-period analysis. This helps distinguish gradual deterioration, stuck sensors, idle periods and isolated corrupt samples. Separate units into separate axes or charts.

Missingness chart

Plot the percentage missing for each sensor, then compare missingness by family, quality flag and day. Missingness may depend on a faulty sensor or operating state. Filling every gap with a global mean can hide that structure.

Correlation heatmap

Use training-period numeric features after unit normalization. Correlation can identify redundant measurements, but correlated does not mean causal. A strong relationship with a future-outcome field is leakage, not a useful discovery.

Class comparisons

Compare training distributions by health_priority while accounting for family and operating state. If vibration rises before some failures, check how often normal operation has similar values. A useful predictor needs separation without creating excessive false alerts.

Avoid these mistakes

Do not compute scientific summaries across Celsius and Fahrenheit values together. Do not use a pie chart for a continuous sensor trend. Do not draw lines across different machines. Do not manufacture variation in a flat signal. Save plots with title, units, time zone, selected population and sample count.

Save

Create outputs/figures and export your charts. Write one plain-language conclusion and one limitation beneath each chart.

Clean data with a written decision policy

Order matters

Resolve machine aliases; parse UTC timestamps; parse numeric strings; identify -9999 sentinels; normalize temperature and pressure units; check validity; then resolve duplicate packets. Identifying sentinels before conversion prevents turning -9999 Fahrenheit into a different invalid number.

Units

Use Celsius = (Fahrenheit - 32) * 5 / 9. Divide kPa by 100 to obtain bar. Vibration is velocity in mm/s; do not call it acceleration in m/s squared. Convert a decimal comma such as 2,75 to 2.75 only in the documented sensor field. Do not indiscriminately remove punctuation from all data.

Duplicates

Identical retransmissions can collapse to one normalized observation. Conflicting packets share an ID but disagree in content. Without a trusted sequence or receipt timestamp, choosing the first shuffled row is arbitrary. The starter excludes every conflicting group and reports it. You may propose a different evidence-based policy and compare its effect.

Invalid and missing values

The starter converts gross invalid values to missing and excludes BAD packets from its baseline. These broad plausibility bounds are practice assumptions, not safety limits. UNCERTAIN packets are retained as a documented choice. Distinguish input corruption from a physically unusual but valid signal. Do not drop all rows with any missing sensor by default.

Stuck readings and gaps

Flag repeated constant readings over a sustained period. Investigate whether the machine is idle or the sensor is stuck. Do not blindly add random noise. A future extension can add a past-only stuck-sensor indicator. Forward filling must be within one machine and bounded in time; never backward-fill from the future.

Save and explain

Save cleaned_features.csv and cleaning_report.json with counts for missing conversions, invalid times, unknown identities, duplicate groups and exclusions. Preserve the raw source. Re-run all audit checks on cleaned data and reconcile every removed row.

Engineer features available at prediction time

Current readings

Start with normalized temperature, vibration, RPM, current, load, pressure, flow, ambient temperature and hours since service. These form a transparent baseline. Use machine_type and plant as categories if appropriate. Do not begin with dozens of features before you understand the measurements.

Historical features

For each canonical machine, order records by time and calculate past-only rolling mean, standard deviation, min/max and change from the previous reading. Suitable practice windows are 30, 60 and 120 minutes, which contain roughly 3, 6 and 12 readings at the intended cadence. Time-based windows are safer when observations are missing.

What past only means

At 10:00 you may use the current 10:00 packet and earlier readings. You may not use 10:10 or the upcoming failure time. A trailing rolling window can include the current packet; a centered window cannot be used for this prediction task. Group by machine before lagging or rolling.

Do not bridge long outages

Calculate time_since_previous_reading. If a gap is too long, mark history incomplete or reset the window according to your documented rule. An hour since service may reset after completed maintenance; respect this rather than smoothing it away.

Fit transformations safely

The baseline median imputer and missing indicators learn from training only. One-hot encoding maps machine family and plant while tolerating unseen categories. Scaling is important for logistic regression, but tree models do not require it. Place preprocessing and the estimator inside one scikit-learn Pipeline.

Identity and generalization

The starter does not use packet ID or machine ID as predictors. IDs can encourage memorization. A future held-out-machine experiment is useful if deployment will include new machines. The provided chronological test primarily measures later data from known machines.

Split by time before model fitting

Exact split

Training: January 1 at 00:00 UTC inclusive to January 10 exclusive. Validation: January 10 inclusive to January 12 exclusive. Test: January 12 inclusive to January 15 exclusive. Read these boundaries from split_plan.json rather than typing different dates in separate notebooks.

Why no random split

Adjacent readings from one machine and failure episode are strongly related. Random splitting can place almost identical neighboring observations into training and testing, making the model seem better than it is. The CSV is shuffled for cleaning practice; sort by observed time for splitting.

Purge the outcome horizon

For each partition, keep observations only when observation_time plus 120 minutes is strictly before its end. This conservative implementation removes the final two hours, including the boundary row. It prevents training labels from using failures that occur in validation, and prevents validation labels from using test-period outcomes.

What each partition does

Training fits model parameters and preprocessing. Validation chooses features, model settings, probability thresholds and alert persistence. Test is opened once after these decisions are frozen. If you repeatedly adjust the model based on test results, that test is no longer an independent final evaluation.

Rolling history across boundaries

Past training observations may supply trailing history at the start of validation because that history would already exist at prediction time. Future validation or test observations may never alter training features or fitted transformations. The simple starter uses current readings only, avoiding this extra implementation complexity.

Checks to run

Assert unique packet IDs in each split; empty intersections between split IDs; non-overlapping chronological intervals; known labels only; no DOWN rows; canonical IDs present in registry; full outcome horizon inside each partition. Print class counts by split and check that rare classes remain present.

Save

Export train.csv, validation.csv and test.csv under outputs. Save boundaries, purge policy, excluded counts and random seeds in your experiment record. Do not oversample validation or test.

Train a baseline then improve it

Begin with a baseline

The optional notebook fits a most-frequent DummyClassifier and a small RandomForestClassifier. The dummy shows how misleading accuracy can be. A modest tree baseline checks whether the cleaned current readings carry useful information. It is not a finished production model.

Separate X from y

y is health_priority. X is an explicit allowlist of current normalized numeric readings plus machine_type and plant. Never select all columns and merely delete one target column: future-outcome fields can remain unnoticed. The notebook constructs X from an allowlist.

Missing data

The pipeline imputes numeric fields with training medians and adds missingness indicators. It one-hot encodes categorical fields and ignores unseen categories during prediction. Training-only fitting avoids passing information from validation or test into model preparation.

Class imbalance

The starter forest uses balanced class weights to give rare classes more attention. This does not guarantee adequate Critical recall. Compare weighted and unweighted models on validation. If using resampling, perform it only inside training folds; never synthesize test examples or resample before splitting.

Next experiments

Compare logistic regression with scaling, a shallow decision tree and the forest. Add past-only trend features in a separate experiment. Change one factor at a time. Keep a table of experiment name, features, parameters, training dates, validation precision/recall and limitations.

Time-aware tuning

If you use cross-validation, create expanding chronological folds with at least a two-hour purge before each validation boundary. Use class/event counts to ensure every fold is meaningful. Ordinary shuffled K-fold validation is unsuitable for these sequential observations.

Save

Write validation_metrics.json and validation_predictions.csv. Keep your code and environment versions. Do not report a score until you have actually run the experiment. This package contains no precomputed model results.

Evaluate predictions as an operations problem

Per-class measures

Precision asks how many alerts of a class were correct. Recall asks how many real cases of that class were detected. F1 balances precision and recall. Macro-F1 gives each class equal weight. A confusion matrix shows which classes are confused; use both counts and normalized percentages.

Critical cases

Missing a Critical event matters, but an alert every minute is also unusable. Report Critical precision and recall together, and plot a one-versus-rest precision-recall curve. Do the same for any-warning versus Normal if that matches your operational routing. State which class is positive.

Episode metrics

One failure can produce multiple adjacent warning rows. Group consecutive alerts per machine into episodes using a documented gap/cooldown rule. Count false alert episodes per machine-day and unique failures detected with warning before failure time. Define a matching window and count one event only once.

Lead time

For each matched failure, measure failure time minus the first qualifying prior alert. Report median and distribution, together with event recall. A warning after failure is not early detection. The 10-minute sampling interval limits timing precision; do not claim second-level forecasting from this dataset.

Thresholds

A classifier probability is not automatically a calibrated failure probability. Select alert thresholds on validation according to acceptable missed events and false alerts. Consider persistence across multiple observations, but recognize that persistence delays alerts and may miss sudden failures. Record both effects.

Compare subgroups

Report performance by family, plant, operating state, missingness and quality flag. Check distribution drift between training and the final period. This synthetic dataset includes a late-period shift, so aggregate scores may hide a change in behavior.

Final test

Freeze the full pipeline and alert policy first, then run the guarded final-test cell once. Save all results including bad ones. A high synthetic test score does not establish readiness for physical machine control.

Explain results and write a model card

What the model learned

Inspect feature importance or permutation importance using a validation sample. Importance indicates predictive association, not a verified mechanical cause. Correlated features can share importance. A temperature-related prediction does not prove a cooling fault without investigation.

Error review

Examine examples of a missed Critical event, a false Critical alert, a correctly predicted Suspect case and a confusing Normal case. Plot their preceding two-hour histories. Ask whether the error came from corruption, missing context, sudden failure, inadequate features or an unsuitable decision threshold.

Business insight

Write findings such as: vibration trend was useful for some bearing events in this synthetic experiment, but sudden failures remained difficult. Replace that example with your actual measured findings. Do not claim downtime saved or repairs prevented unless a controlled evaluation supports it.

Model card contents

Include intended purpose, training data provenance, dates, target semantics, excluded records, model version, preprocessing, features, split rules, per-class and event metrics, known weaknesses, supported machine families, monitoring plan and conditions requiring human review.

Reproducibility

Record package versions, code version, dataset checksums, seeds, parameters and decision thresholds. A notebook should run from a clean kernel in order. Keep exploratory dead ends in your experiment notes, but present a clear final pipeline that can be reproduced.

Prepare a local prediction service later

Deployment boundary

First complete offline evaluation. Only then build a local prediction API in the practice folder. A practice model must not overwrite FactoryPulse authentication, change machine assignments, control machinery or bypass the existing telemetry receiver.

Save the whole pipeline

Persist preprocessing plus the estimator together, along with a JSON schema and model metadata. Saving only the forest loses the imputer and category encoding. Load only trusted model artifacts you created; serialized Python models can execute code when loaded.

Validate each request

Require a canonical machine ID, UTC observation time, known units and expected feature fields. Reject malformed or stale data, or return an explicit insufficient-data state. Do not interpret a missing reading as Normal. Apply the same cleaning and feature logic used offline.

Example response fields

Return machine_id, observed_at_utc, predicted_priority, model_version, data_quality, feature_window and an explanation of missing context. Include calibrated probabilities only after checking calibration. A stale or unknown machine must not receive a fabricated confident diagnosis.

Where it could fit

The existing operational path stays AI Simulator to FactoryPulse receiver to committed MySQL records to dashboards. A later inference worker can read authorized recent records and store model predictions separately. Predictions must not replace the original readings. Both model and rule-based alerts should carry their source and time.

SOP and notification routing

After separate integration approval, Suspect predictions could notify the assigned Operator, Supervisor and Maintenance; Critical could additionally notify the responsible Plant Manager. Retrieve an approved machine-specific SOP, show the reason and require human review. Model output must not invent shutdown steps or authorize restart.

Monitor

Track request failures, freshness, missing features, prediction latency, class proportions, drift and eventual verified outcomes. Deduplicate repeated alerts into incidents and define a rollback. One successful API request is not an end-to-end reliability test.

Troubleshoot and check completion

File not found

Check the BASE path printed by cell 1 and confirm telemetry_raw.csv is directly inside it. You may have an extra nested folder after extraction. Keep relative references consistent. Never point the notebook at a live database file.

Module not found

The notebook is probably using a different Python environment. Select the extracted folder’s .venv interpreter and install requirements using that exact Python. Restart the kernel after installation.

Date parsing or mixed numbers

Read text first. Use UTC for both ISO and alternate timestamps. Replace decimal commas only in vibration, mask sentinels before conversion and count invalid conversions. Record failures instead of silently coercing a large fraction away.

Model seems almost perfect

Check future fields, duplicated IDs across partitions, random splitting, global preprocessing and use of post-repair records. Also remember the data is synthetic. A very high score can reflect generator patterns rather than useful industrial generalization.

Model predicts only Normal

Inspect rare-class counts and per-class recall. Compare class weights, better historical features and thresholds on validation. Do not balance the test set or invent positive examples to improve the final score.
